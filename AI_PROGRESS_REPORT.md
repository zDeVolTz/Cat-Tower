## 5. Текущее состояние архитектуры

Краткая схема (текущая реальность):

Game Loop (gameLoop.js)
 │
 ├─> Старая физика (PhysicsEngine.js -> Solvers)
 │    └─> Вычисляет состояние для state.blocks (POJO объекты)
 │
 ├─> Обработка ввода (physics.js / handleDrop)
 │    ├─> Добавляет блок в state.blocks
 │    └─> Добавляет тот же блок в state.physicsWorld (Новый слой)
 │
 └─> Рендеринг (renderer.js)
      └─> Отрисовывает основываясь на state.blocks

- **Игровая логика:** `gameState.js`, `physics.js`, `gameLoop.js`
- **Физика:** 
  - *Старая (активная):* `PhysicsEngine.js`, `FallingSolver.js`, `StabilitySolver.js` и т.д.
  - *Новая (пассивная):* `PhysicsWorld.js`
- **Состояние башни:** Массив POJO-объектов `state.blocks`. Он же продублирован по ссылкам внутри `state.physicsWorld.bodies`.
- **Рендеринг:** Опирается исключительно на `state.blocks`.

## 9. Важные архитектурные наблюдения

**ВНИМАНИЕ для следующих этапов:**
В репозитории существует `src/game/physics/Block.js`, однако этот класс фактически является **мертвым кодом** в основном геймплее. Все игровые блоки создаются литерально как POJO-объекты (`const placed = { x, y, width, ... }`) в `physics.js` и `gameState.js`. 

Когда потребуется вызывать физические методы (например, `body.applyForce()`), текущие объекты в `PhysicsWorld.bodies` не будут их иметь, так как они не являются экземплярами класса. Потребуется либо рефакторинг создания блоков (инстанцирование реального `PhysicsBody`), либо переход на компонентную систему, не привязанную к методам объекта.
